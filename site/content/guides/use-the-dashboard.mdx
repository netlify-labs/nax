# Use the dashboard

The dashboard is a local browser workbench for browsing workflows, previewing dry runs, starting real runs, watching structured events, and handing completed artifacts to follow-up agents. It exists because long multi-agent workflows are easier to inspect as stateful runs than as terminal output alone.

## Surfaces

| Surface | What it does |
| --- | --- |
| Workflow list | Reads the same workflows as `nax list`. |
| Graph canvas | Shows one chip per instance, inputs, submit mode, and step/instance status. |
| Dry Run | Runs `nax run <flow> --dry --force` through the local API. |
| Run | Starts the workflow after browser confirmation. |
| Run agent | Starts a standalone provider run with its own model and effort settings. |
| Instance configuration | Adds, edits, or removes exact provider/model/effort tuples on each runnable step. |
| Recent runs | Reads `.nax/workflows` and highlights resumable or completed runs. |
| Run details | Shows results, prompt source, artifacts, copy/open actions, and follow-up controls. |

## Verify the Agent Runner site

When the dashboard starts, the terminal lists every `.netlify/state.json` link found in the repository and marks the site selected for Agent Runner execution. The dashboard header repeats that target in the **Agent runs** menu, where you can inspect every local link and open the corresponding Netlify Agent Runs page.

In a monorepo, the repository-root link is not automatically the run target. If exactly one discovered `netlify.toml` contains a package-manager `--filter`, `nax` selects that app and its adjacent `.netlify/state.json`. The startup output and dashboard menu include this selection reason, and the run confirmation names the exact Netlify site before remote work begins.

## Develop the dashboard UI

```sh
node src/cli/nax.js dashboard --no-open --port 53734
NAX_DASHBOARD_API_URL=http://127.0.0.1:53734 npm run dashboard:dev
```

Open the Vite URL with the printed token:

```text
http://127.0.0.1:5173/?token=<token>&workflow=do-next
```

<Callout type="warning">
  Mutating dashboard endpoints require the token embedded in the opened URL or supplied as `x-nax-token`.
</Callout>

## Follow up from a run

In Run details, choose **Send to next agent**. The composer requires fresh instructions, defaults to the last meaningful artifact, and lets you choose which workflow, step, runner, session, or result artifacts to include.

## Configure instance lineups

Each runnable step card shows one chip per instance. Existing bare-provider
flow entries load as **Auto** chips and stay Auto unless you edit them. Open a
chip's caret to pin its exact model and effort, or remove that tuple without
affecting another instance of the same provider.

Choose **Add agent** on a step to build a cartesian lineup from one provider,
multiple models, and multiple efforts. The picker preselects that provider's
flagship model and highest effort. Quick presets cover one flagship from every
provider, one model at every effort, or every model from one provider. Adding
more than six instances to a step requires confirmation.

Follow-up step chips are read-only. They inherit the surviving instances from
the first input step and continue each instance's own runner session. During a
run, chips are keyed by exact instance id, so two Claude models can show
different statuses. A mixed result is visibly marked **Completed with
failures** rather than being shown as an all-green step.

The follow-up composer opens its configuration drawer and initializes the
matching provider from the selected source run or session. Changing it is an
intentional override for the new submission. Run history and details keep the
requested model/effort separate from the backend-observed `agent_config`.

Pinned settings with transport Auto resolve to the Netlify API. GitHub
transport disables model and effort configuration because the pinned GitHub
Action supports provider selection only.

For work that does not need a workflow, choose **Run agent** in the header.
Select one provider, enter the prompt, and use the same server-owned model and
effort catalog. The standalone run is persisted and appears in Recent runs
with the resolved provider, model, and effort.
